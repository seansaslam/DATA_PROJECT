Arm each source the way an ingestion tool needs it, then answer the question that actually decides a pipeline design: if this ran right now, how many rows would it move, and would it catch the deletes? Nothing is written anywhere — the read extracts, counts and records the number. Turn the watermark off to read the same window repeatedly — useful for showing that a strategy is deterministic. Switching strategy always clears the watermark, so the next read baselines; the rebuild switch additionally drops and recreates the source tables, which throws the seeded production history away.

What each strategy does

FULL Read every row, every time. Needs nothing enabled on the source and cannot be wrong. The right answer for both master tables.

INCREMENTAL WHERE UPDATED_TS > watermark. Cheapest, and structurally blind to hard deletes — which is the lesson.

CT Change Tracking. CHANGETABLE says which rows changed and that a row was deleted, but not what it held, so the reader joins back to the base table. Watermark is a version number.

CDC Change Data Capture. The capture table carries the values themselves, so a deleted row's contents survive. Watermark is an LSN. Needs a one-time sysadmin enable and a running Agent on-prem.
